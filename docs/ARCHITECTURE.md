# Architecture

## Stack

- **Next.js 15 (App Router, TypeScript, Tailwind CSS 4)**. Server components fetch data; server actions handle mutations.
- **Supabase**: Postgres (data + authorization), Auth (email/password, Google OAuth), Storage (photos), Realtime (chat).
- The landing page is a single static HTML file (only the product name changed), served at `/` (`next.config.ts` rewrite).

Why: the existing project was a single static `index.html` with no framework, so there was no stack to preserve.
Next.js + Supabase was chosen as a conventional, typed setup that hosts the static landing page unchanged.

## Where security lives

Authorization is enforced in the database, so it holds even if someone calls the Supabase API directly:

| Rule | Mechanism |
| --- | --- |
| Only verified, unsuspended members of an active institute can publish | `listings_insert` RLS policy + `is_verified_member()` |
| Users edit only their own listings; can't change seller, institute, demo flag | RLS + column grants + `listings_guard` trigger |
| Moderator-removed listings can't be re-published by the seller | `listings_guard` |
| Photos only in the uploader's own folder; max per listing | Storage policies + `listing_images_guard` |
| Only participants read/write a conversation; sender can't be spoofed; blocks respected | RLS + `messages_guard` |
| Contacting/offering requires verification | `start_conversation()` / `make_offer()` |
| Offer turn order, expiry, one pending per buyer, one accepted per listing | `respond_offer()` row locks + partial unique indexes |
| Verification-critical profile fields (institute, verified flag, suspension, roles) | not granted to users at all |
| Admin/moderator actions | `SECURITY DEFINER` functions calling `require_staff()` / `is_admin()`; roles in `user_roles` |
| Institute email codes | generated and HMAC-hashed on the server; DB functions callable by the service role only; 5/hour per account, 3/hour per email, 5 attempts |
| Abuse limits | `rate_limit_hit()` / `consume_rate()` (DB-backed): messages, listings, offers, conversations, reports, manual reviews per user; login, signup, reset, codes, contact per IP (server) |
| Helper functions only answer about the caller | `caller_is_end_user()` checks the request role; internal checks use `has_role()` |
| Listing saves are atomic and idempotent | `save_listing()` |

The UI hides buttons too, but only for convenience.

**Rule for new migrations:** Supabase grants every new table and function to `anon` and `authenticated` by
default. End each migration with explicit `revoke`/`grant` statements and add tests (see docs/DEPLOYMENT.md).

**Headers:** app pages get a per-request nonce CSP from `src/middleware.ts`; the static landing page gets a CSP
with hashes of its inline scripts (`landing/csp.json`, regenerated by `npm run landing`). HSTS and other headers
are set in `next.config.ts`.

Tests: `npm run test:db` runs the real migrations in an embedded Postgres (PGlite) on a Supabase stub and
exercises these rules as anonymous, normal, unverified, suspended, moderator and admin users (51 tests,
including one regression test per audit finding). `npm run test:unit` covers redirects, money, search
queries, error mapping, CSP, env validation and photo re-encoding (30 tests).

## Data model

`institutes` → `institute_memberships` ← `profiles` (1:1 with `auth.users`) → `user_roles`

`listings` (sale or wanted; price in integer **paise**, `currency`) → `listing_images`, `saved_listings`

`conversations` (one per listing × initiator) → `conversation_participants` (read markers), `messages`, `offers`

`notifications` (created by triggers only), `reports`, `moderation_actions`, `audit_events`, `blocks`, `contact_messages`, `app_settings`

## Multi-institute design

- Every listing and conversation carries `institute_id`; memberships are per institute with their own status.
- Institute rules (email domains, manual review, offers on/off, public browsing, image limits) are rows in
  `institutes`, editable in `/admin/institutes`, not code.
- The app reads the default institute from `NEXT_PUBLIC_DEFAULT_INSTITUTE_ID`; no institute name is hardcoded in pages.
- Cross-campus discovery is behind `app_settings.cross_campus_enabled = false`. The homepage shows a non-interactive
  "Other campuses — coming soon" panel only. See `docs/INSTITUTES.md` to onboard an institute.

## Offers vs. auctions

Offers are a negotiation tool (accept / decline / counter, 48 h expiry, no money, no obligation). An accepted offer
reserves the listing. There is no auction code; `listing_type` deliberately has no `auction` value. See `docs/AUCTIONS.md`.

## Payments

None. No checkout, no card data, no payment-success screens. `app_settings.online_payments_enabled = false`.
